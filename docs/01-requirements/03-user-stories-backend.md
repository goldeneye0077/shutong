# Backend 用户故事

## 1. 服务目标

backend 是唯一公共业务 API，负责认证、权限、对象台账、文件元数据、巡检状态、问题闭环、审计和报告任务管理，同时负责向 data-service 写入和读取任务状态。

## 2. 用户故事

### 2.1 认证与权限

- 作为平台管理员，我希望创建本地账号并分配角色，以便在首版不依赖 SSO 的情况下即可运行。
- 作为用户，我希望通过统一的登录与令牌刷新流程访问 API，以便前端安全调用受保护资源。
- 作为系统管理员，我希望所有受保护接口都经过 RBAC 判定，以便控制不同角色的数据可见性和操作权限。

### 2.2 业务状态管理

- 作为运维人员，我希望通过 API 维护对象台账、责任归属和基础参数，以便前端展示统一视图。
- 作为运维人员，我希望上传配置文件时同时创建版本元数据和处理任务，以便后续解析和校验可追踪。
- 作为用户，我希望查询巡检任务状态、解析状态和报告导出状态，以便知道后台处理进度。

### 2.3 工作流与审计

- 作为安全复核人员，我希望对例外申请和整改销项执行审批，以便在业务 API 层保留明确的流程边界。
- 作为审计人员，我希望通过 API 查询导出和审批等关键操作日志，以便支持追责和取证。

### 2.4 与 data-service 协作

- 作为 backend，我希望将需要处理的工作项写入 `job_queue`，并读取结果表更新用户可见状态，以便隔离实时 API 与重任务处理。
- 作为 backend，我希望不直接执行解析和规则校验，以便保持 API 轻量和边界清晰。

## 3. 后端验收标准

- 所有公开接口位于 `/api/v1` 下并由 OpenAPI 描述。
- 登录、刷新令牌、获取当前用户信息构成最小可运行认证链路。
- 上传配置、创建巡检、创建报告任务后均会生成相应元数据和 job_queue 记录。
- 审批、导出、登录、关键配置变更均写入审计日志。
- 前端不需要访问 data-service 的任何内部接口即可完成业务闭环。
